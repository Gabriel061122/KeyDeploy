# Requisitos de KeyDeploy

## 1. Propósito y alcance

KeyDeploy ayuda a una persona sin conocimientos técnicos a describir una aplicación, obtener propuestas de infraestructura asistidas por IA, comprobarlas con reglas de la plataforma y completar una contratación simulada. La aplicación calcula y explica los precios; la IA recomienda, pero no valida compatibilidades, decide precios ni ejecuta contrataciones.

En el alcance de esta versión, los pagos, despliegues, recursos y datos de tráfico son simulados. No se realizan cobros reales ni se aprovisionan máquinas en AWS, Azure u otros proveedores. El catálogo contempla productos de computación, almacenamiento, bases de datos, redes, seguridad, copias de seguridad, monitorización, computación IA, servicio IA y soporte (SOPORTE).

Los requisitos se basan en el análisis funcional del PDF `UT1_PLANTILLA_B_DOCUMENTACION_PROYECTO_2026_2027.docx.pdf`. Las notas anteriores del directorio `Análisis de productos/` contienen ideas de créditos, suscripciones anuales, pagos externos y aprovisionamiento real que no forman parte del alcance aquí descrito; no se consideran requisitos de esta versión.

**Prioridades:** Alta = necesaria para el flujo principal de la primera versión; Media = necesaria para completar la gestión y supervisión de la plataforma.

## 2. Requisitos funcionales (RF)

| ID | Requisito | Actor / origen | Prioridad | Criterio de aceptación |
|---|---|---|---|---|
| RF01 | El sistema permitirá iniciar sesión a los usuarios registrados y limitará las operaciones disponibles según sus roles: CLIENTE, ARQUITECTO, AUDITOR o ADMINISTRADOR. | Usuario registrado | Alta | Dado un usuario activo con credenciales válidas, al iniciar sesión se crea una sesión asociada a su rol. Si intenta una operación no autorizada, el sistema la deniega. |
| RF02 | El CLIENTE autenticado podrá crear un Proyecto indicando descripción funcional, región, presupuesto máximo y número esperado de usuarios. | CLIENTE | Alta | Si falta alguno de los cuatro datos obligatorios o alguno no tiene un valor válido, el Proyecto no se guarda y se informa del campo que debe corregirse. Si son válidos, queda asociado al CLIENTE. |
| RF03 | El sistema podrá proponer Requerimientos estructurados a partir de la descripción del Proyecto. Cada requerimiento contendrá campo, operador, valor y condición obligatoria u opcional; el CLIENTE podrá revisarlo y confirmarlo o ajustarlo. | CLIENTE / Servicio de IA | Alta | Tras la confirmación, el Proyecto conserva los requerimientos revisados con sus campos y valores. Una respuesta de IA que no tenga el formato esperado no se guarda como requerimientos confirmados. |
| RF04 | El sistema solicitará al Servicio de IA una o varias propuestas de Arquitectura a partir de los requerimientos confirmados y del catálogo pertinente. | CLIENTE / Servicio de IA | Alta | Para una solicitud válida, el sistema registra cada respuesta estructurada como borrador asociado al Proyecto. La respuesta incluye los productos y configuraciones recomendados; no se acepta como válida únicamente por haber sido generada por la IA. |
| RF05 | El sistema validará las propuestas con reglas deterministas: unidades, requisitos mínimos, disponibilidad en la región exigida y compatibilidad entre productos. El ARQUITECTO podrá revisar las propuestas válidas, ajustar su configuración y registrar la revisión. | Aplicación / ARQUITECTO | Alta | Una propuesta que incumple una regla obligatoria queda marcada como no válida y muestra al menos un motivo concreto. Una propuesta ajustada se vuelve a validar antes de quedar revisada técnicamente. |
| RF06 | El CLIENTE podrá comparar propuestas revisadas, modificar las opciones permitidas y seleccionar una Arquitectura. La selección aceptada quedará congelada. | CLIENTE | Alta | Solo se puede aceptar una propuesta válida y revisada. Tras aceptarla, cualquier modificación se tramita como una nueva propuesta, que debe validarse y revisarse de nuevo. |
| RF07 | El CLIENTE podrá añadir, ajustar y quitar líneas del Carrito a partir de una Arquitectura aceptada, y consultar el coste estimado actualizado. | CLIENTE | Alta | Después de cada modificación se recalcula el total y se comprueban dependencias y compatibilidad. No se permite añadir un producto retirado o no disponible en la región requerida. |
| RF08 | El sistema emitirá Presupuestos con el detalle de líneas, configuración, precios unitarios, conceptos únicos y recurrentes, total y fecha de caducidad. El presupuesto conservará una copia de los precios y condiciones empleados; no se calculan impuestos en esta simulación. | CLIENTE / Aplicación | Alta | Al emitirse, el presupuesto muestra el desglose y la fecha de caducidad. Un cambio posterior en el catálogo no cambia sus líneas ni sus precios. |
| RF09 | Si el total de una propuesta supera el presupuesto máximo del Proyecto, el sistema mostrará una advertencia y, cuando existan, al menos una alternativa válida de menor coste. El aviso no impedirá emitir el presupuesto ni contratarlo. | Aplicación | Alta | Dado un total superior al máximo indicado, el sistema muestra el aviso. Si el catálogo permite una alternativa válida más económica, también la presenta; si no existe, lo indica y permite continuar. |
| RF10 | El CLIENTE podrá convertir un Presupuesto vigente en Pedido y efectuar un pago inicial simulado que cubra el primer periodo mensual y los conceptos únicos. Después, el sistema registrará como máximo un cargo simulado por periodo mensual activo para los conceptos recurrentes contratados. | CLIENTE / Aplicación | Alta | Un presupuesto caducado no genera un Pedido. Si el pago inicial simulado falla, el Pedido no queda pagado y no se crea el Despliegue. Los cargos posteriores quedan desglosados y no duplican el mismo periodo. |
| RF11 | Un Pedido pagado podrá originar un Despliegue simulado con sus recursos. Mientras esté activo, el sistema registrará tráfico simulado y permitirá al CLIENTE consultar un gráfico, cambiar la aplicación asociada y consultar el estado y los cargos. | CLIENTE / Aplicación | Alta | Tras completar el pago inicial se crea un Despliegue con estado y recursos. El gráfico presenta registros de tráfico asociados a ese Despliegue. En ningún caso esta operación aprovisiona infraestructura real. |
| RF12 | El ADMINISTRADOR podrá crear, consultar, modificar y retirar productos del Catálogo, incluyendo sus atributos específicos, tarifas unitarias y disponibilidad por proveedor y región. | ADMINISTRADOR | Media | El sistema valida los campos comunes y los específicos del tipo de producto antes de guardar. Cada cambio de catálogo queda registrado y no altera presupuestos emitidos ni periodos mensuales ya iniciados. |
| RF13 | El AUDITOR podrá consultar y filtrar los registros de auditoría en modo de solo lectura. Cada registro mostrará, cuando corresponda, actor, acción, fecha, elemento afectado y valores anterior y nuevo. | AUDITOR | Media | El AUDITOR puede filtrar por usuario, acción o fecha. No dispone de una operación para modificar o eliminar registros. |
| RF14 | Una persona sin cuenta podrá registrarse como CLIENTE. El registro público no permitirá asignar roles privilegiados. | Persona no registrada | Alta | Con datos válidos y correo no utilizado, se crea una cuenta con el único rol CLIENTE. Una petición que intente asignar ADMINISTRADOR, ARQUITECTO o AUDITOR es rechazada o ignora esos campos. |
| RF15 | El CLIENTE podrá añadir SOPORTE a un Despliegue activo propio o solicitar su cancelación. El cambio tendrá efecto desde el siguiente periodo mensual. | CLIENTE | Media | El sistema registra la solicitud y su fecha de entrada en vigor. El cargo del periodo en curso no se modifica y el siguiente cargo refleja el alta o baja. |
| RF16 | El ADMINISTRADOR podrá crear y actualizar cuentas internas y asignar o revocar roles autorizados. Las operaciones de gestión de roles quedarán auditadas. | ADMINISTRADOR | Media | Al guardar un cambio válido, los permisos efectivos de la cuenta coinciden con los roles asignados y se genera un registro de auditoría. El registro público de CLIENTE no puede otorgar roles internos. |
| RF17 | El sistema permitirá que el CLIENTE consulte y modifique solo sus propios Proyectos, Presupuestos, Pedidos y Despliegues. El ARQUITECTO accederá a los elementos que deba revisar por su rol; el Servicio de IA no tendrá acceso directo a registros persistentes ni recibirá identificadores de cuenta. | Aplicación | Alta | Una solicitud de un CLIENTE sobre un recurso ajeno se deniega. La petición enviada al Servicio de IA contiene únicamente los datos mínimos para la recomendación y no incluye identificadores de cuenta ni credenciales. |
| RF18 | Si el Servicio de IA devuelve un error, una respuesta incompleta o datos que no cumplen el esquema esperado, el sistema informará de que no se pudo generar una propuesta y conservará el Proyecto y sus requerimientos confirmados. | Aplicación / Servicio de IA | Alta | Ante un error o respuesta inválida no se crea una Arquitectura aceptable para el cliente ni se permite añadirla al Carrito; el fallo queda registrado para su diagnóstico. |

## 3. Requisitos no funcionales (RNF)

| ID | Requisito | Categoría | Cómo se comprobará |
|---|---|---|---|
| RNF01 | La validación de requisitos y propuestas, la comprobación de compatibilidad y el cálculo de precios se ejecutarán en la aplicación. La respuesta de IA no podrá sustituir ni alterar estas reglas. | Fiabilidad | Revisión del código y pruebas con respuestas de IA que incluyan productos incompatibles, precios inventados o requisitos incumplidos. |
| RNF02 | Las contraseñas se almacenarán mediante un mecanismo de hash adecuado. Las credenciales y secretos de configuración permanecerán en `.env`, excluido del repositorio; `.env.example` no contendrá secretos reales. | Seguridad | Revisar almacenamiento de contraseñas, `.gitignore`, `.env.example` y el contenido versionado del repositorio. |
| RNF03 | Las acciones sensibles conservarán trazabilidad con actor, acción, fecha, elemento afectado y, si aplica, valores anterior y nuevo. Los registros de auditoría no serán editables desde la aplicación. | Trazabilidad | Ejecutar acciones sobre catálogo, roles, propuestas y pedidos; consultar sus registros y comprobar que el AUDITOR solo puede leerlos. |
| RNF04 | Las operaciones habituales de catálogo y Carrito responderán en menos de 2 segundos en al menos el 95 % de las solicitudes bajo el entorno de pruebas previsto. El tiempo de respuesta externa de la IA no forma parte de esta medición. | Rendimiento | Medir una muestra documentada de solicitudes de catálogo y Carrito con herramientas del navegador o registros de la aplicación; calcular el percentil 95. |
| RNF05 | El acceso a datos se controlará por usuario propietario y rol. La información enviada a servicios externos se limitará a la necesaria para realizar la operación solicitada. | Seguridad / privacidad | Probar acceso cruzado entre cuentas y revisar la carga enviada al Servicio de IA para verificar que no contiene identificadores de cuenta, credenciales ni datos ajenos a la recomendación. |

## 4. Reglas de negocio (RN)

| ID | Regla | Elementos afectados | Observaciones / casos límite |
|---|---|---|---|
| RN01 | Un Presupuesto emitido conserva los precios y las configuraciones con los que se generó. | Presupuestos, Catálogo | Una modificación posterior del Catálogo no actualiza el Presupuesto emitido. |
| RN02 | Un Presupuesto caducado no puede convertirse en Pedido. | Presupuestos, Pedidos | El CLIENTE debe emitir un nuevo Presupuesto con precios vigentes. La duración exacta de la vigencia queda pendiente de definir. |
| RN03 | Los cambios de tarifa no modifican presupuestos emitidos ni periodos mensuales ya iniciados; las nuevas tarifas se aplican a presupuestos futuros y al siguiente periodo mensual. | Catálogo, Presupuestos, Pagos, Despliegues | Se adopta esta regla porque es coherente con RN01 y RN15. El PDF también contiene una frase aislada que parece indicar que una actualización de tarifas caduca un Presupuesto; esa frase contradice ambas reglas y se considera un error de redacción pendiente de corregir en el documento fuente. |
| RN04 | Todos los requisitos marcados como obligatorios deben cumplirse en la Arquitectura aceptada. | Requerimientos, Arquitecturas | Si el catálogo no permite satisfacer un requisito obligatorio, la propuesta no puede aceptarse y se informa del motivo. |
| RN05 | No se puede contratar un producto retirado o no disponible en la región exigida por el Proyecto. | Catálogo, Requerimientos, Arquitecturas, Carrito | La disponibilidad se comprueba también al validar cambios y antes de emitir el Presupuesto. |
| RN06 | La IA propone; la aplicación valida compatibilidad y requisitos, y calcula los precios. | Arquitecturas, IA, Catálogo | Una respuesta de IA nunca autoriza por sí misma una contratación ni establece una tarifa. |
| RN07 | Superar el presupuesto máximo genera una advertencia y alternativas más económicas, pero no bloquea la emisión del Presupuesto ni la contratación. | Proyectos, Presupuestos | Si no hay alternativas válidas más económicas, el sistema lo comunica. |
| RN08 | La contratación inicial debe dejar un resultado coherente: Pedido, pago simulado y Despliegue se crean como una única operación lógica. | Pedidos, Pagos, Despliegues | Si falla cualquier paso, no queda un Pedido marcado como pagado ni un Despliegue parcial. No se procesa dinero real. |
| RN09 | Cada CLIENTE solo accede a los datos de sus propios Proyectos y recursos asociados. Los roles internos acceden únicamente a las funciones autorizadas. | Usuarios, Proyectos, Presupuestos, Pedidos, Despliegues | Tener una URL o identificador válido no sustituye la comprobación de permisos. |
| RN10 | El tipo de un Producto determina el detalle y los campos específicos que debe contener. | Catálogo | No se guarda un Producto activo si falta el detalle obligatorio correspondiente a su tipo. |
| RN11 | Toda acción sensible queda registrada en auditoría y los registros no pueden modificarse desde KeyDeploy. | Auditoría | Incluye como mínimo cambios de catálogo y roles, revisión de propuestas, emisión de presupuestos, contratación y cambios de estado de Despliegues. El AUDITOR tiene permiso de lectura. |
| RN12 | Una Arquitectura aceptada queda congelada. Cualquier cambio posterior requiere una nueva propuesta validada, revisada y aceptada. | Arquitecturas | Ni el CLIENTE ni el ARQUITECTO pueden editar directamente la versión aceptada. |
| RN13 | El pago inicial simulado cubre el primer periodo mensual y los conceptos únicos. En periodos posteriores se genera como máximo un cargo por periodo activo para los conceptos recurrentes contratados: recursos, SERVICIO_IA y SOPORTE, si corresponde. | Pagos, Despliegues | Los conceptos únicos no vuelven a cobrarse. No se generan cargos recurrentes durante estados detenido, suspendido o cancelado. |
| RN14 | Si falla un cargo mensual, se conceden 3 días de gracia. Si sigue impagado al finalizar ese plazo, el Despliegue se suspende. Al regularizar la deuda, se reactiva automáticamente y comienza un nuevo periodo mensual. | Pagos, Despliegues | Durante la suspensión no se generan cargos recurrentes. |
| RN15 | Cada periodo mensual nuevo utiliza las tarifas vigentes al inicio de ese periodo. Las tarifas no se aplican retroactivamente a periodos ya iniciados. | Catálogo, Pagos, Despliegues | Un cambio de tarifa a mitad de periodo se refleja en el cargo del periodo siguiente. |
| RN16 | El alta o baja de SOPORTE en un Despliegue activo entra en vigor en el siguiente periodo mensual, sin modificar el periodo en curso. | Despliegues, Pagos | Si se cancela a mitad del periodo, el servicio permanece contratado hasta terminar el periodo ya pagado. |

## 5. Decisiones y datos pendientes

Los siguientes detalles no están fijados en el análisis y no deben tratarse como valores acordados:

- La duración exacta de la vigencia de un Presupuesto.
- Las tarifas, límites y variantes concretas de los productos del Catálogo, incluida la tarifa mensual de SERVICIO_IA y los planes de SOPORTE.
- Las métricas concretas que compondrán el tráfico simulado.
- Las reglas exactas para detener o cancelar un Despliegue y el efecto de esas acciones sobre el periodo pagado.
- El conjunto definitivo de datos del formulario de registro.
- La frase conflictiva del PDF sobre caducidad de Presupuestos al actualizar tarifas. La interpretación aplicada aquí es: el presupuesto emitido conserva el precio hasta su propia caducidad, y la tarifa nueva se aplica a operaciones futuras.

El alcance de esta versión excluye créditos de IA, pagos reales, cuotas de suscripciones anuales, integración con pasarelas de pago, aprovisionamiento real de infraestructura y monitorización de servidores reales.
